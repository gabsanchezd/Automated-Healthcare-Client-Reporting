# Technical Architecture

This document describes the technical design of the **Automated Healthcare Client Reporting System**.

The main `README.md` is intentionally recruiter-focused and concise. This document provides the deeper implementation details behind the Power Query ETL, validation framework, VBA automation, report generation, and audit logging.

> All healthcare data used in this project is synthetic.

---

## 1. Architecture Overview

The solution uses Excel as the reporting front end, Power Query as the ETL layer, and VBA as the workflow automation layer.

```text
Yearly Claims CSV Files
        |
        v
Power Query Folder Ingestion
        |
        v
Transformation & Standardization
        |
        v
tbl_ClaimsMaster
        |
   +----+-------------------+
   |                        |
   v                        v
QC / Validation        Reporting Layer
   |                        |
   v                 Executive Summary
PASS / REVIEW          Client Summary
/ ERROR                Claim Detail
   |                        |
   +-----------+------------+
               |
               v
          VBA Automation
               |
        +------+------+
        |             |
        v             v
 Client Workbooks   Refresh Log
```

The workbook is designed around a single standardized master table:

`tbl_ClaimsMaster`

All reporting, validation, and client-specific outputs ultimately depend on this table.

## 3. Power Query ETL

The primary Power Query output is:

`qry_Claims_Master`

The final table is loaded to Excel as:

`tbl_ClaimsMaster`

The ETL process performs the following high-level steps:

1. Read files from the claims folder.
2. Combine yearly CSV files.
3. Promote and standardize headers.
4. Apply data types.
5. Clean nulls and invalid values where appropriate.
6. Merge reusable lookup tables.
7. Create calculated reporting fields.
8. Create aging fields.
9. Create QC fields.
10. Create `Overall QC`.
11. Load the result into the Master Data worksheet.

### Supporting Queries

The project also uses lookup/helper queries such as:

- `qry_StatusLookup`
- folder-combine helper queries generated by Power Query

Only the final master query is loaded to the reporting worksheet. Supporting queries are generally configured as **Connection Only**.

This prevents unnecessary duplicate worksheet outputs and keeps the workbook architecture cleaner.

| Partially Paid | Active |

| Negotiated | Active |
| In Process | Active |
| Pending | Active |

| Needs Review | Review |
| Denied | Denied |
| Reversed | Exception |
| Unknown | Exception |

This separates source-system terminology from reporting logic.

If source statuses change, the mapping can be updated without redesigning the reporting layer.

### Financial Logic

Typical derived metrics include:

**Total Collected**

```text
Initial Payment + Additional Collected
```

**Outstanding Amount**

```text
Allowed Amount - Initial Payment - Additional Collected
```

**Collection Rate**


Calculations are centralized in the ETL layer so the dashboards do not need to repeatedly recreate business logic.

## 6. Aging Logic

Aging is calculated using a fixed historical reporting cutoff to make results reproducible.

The project uses standard aging groups:

- 0-30
- 31-60
- 61-90
- 91-120
- 120+

A null Date of Service produces an unknown aging result rather than an artificial date.

Negative aging values can be identified separately as future-DOS conditions.

This avoids silently forcing invalid dates into normal aging buckets.

## 7. Data Quality Architecture

The validation framework evaluates each claim using multiple independent QC rules.

Examples include:

- QC Missing Claim ID
- QC Missing Entity
- QC Invalid Status
- QC Negative Billed
- QC Negative Collection
- QC Allowed vs Billed
- QC Collected vs Allowed
- QC Balance Reconciliation

The final `Overall QC` field uses a priority structure:

```text
ERROR
  |
  v
REVIEW
  |
  v
PASS
```

If any critical rule returns `ERROR`, the record is classified as `ERROR`.

If there are no critical errors but a review-level rule is triggered, the record is classified as `REVIEW`.

Otherwise, the record is classified as `PASS`.

This prevents lower-severity checks from hiding critical issues.

## 8. Validation Layer

The `modValidation` VBA module summarizes the `Overall QC` field from `tbl_ClaimsMaster`.

It calculates:

- Total Records
- PASS
- REVIEW
- ERROR
- Unclassified

The counts are reconciled against the total record count.

The validation result is then written back to the Control Panel.

Example status logic:

```text
If ERROR > 0
    -> ATTENTION REQUIRED

Else if Unclassified > 0
    -> UNCLASSIFIED RECORDS

Else if REVIEW > 0
    -> REVIEW REQUIRED

Else
    -> VALIDATION PASSED
```

The validation result is also written to the Refresh Log.

## 10. VBA Module Architecture

The VBA solution is separated into modules based on responsibility.

### `modRefresh`

Responsibilities:

- locate `tbl_ClaimsMaster`
- access its QueryTable
- prevent duplicate refreshes
- start the refresh
- update Power Query status
- initialize the event listener

The refresh is started in the background so Excel can remain responsive.

### `CQueryEvents`

`CQueryEvents` is a Class Module that listens for the QueryTable `AfterRefresh` event.

It handles:

- successful refresh completion
- failed refresh completion
- refresh duration
- refresh timestamp
- Power Query status
- Refresh Log entry

A global reference is kept while the query is running so the class instance remains alive long enough to receive the completion event.

### `modValidation`

Responsibilities:

- read `Overall QC`
- count validation categories
- calculate overall validation status
- update the Control Panel
- write validation activity to the Refresh Log

### `modReportGenerator`

Responsibilities:

1. Read the unique entity list from `tbl_ClaimsMaster`.
2. Set `selEntity`.
3. Recalculate Client Summary and Claim Detail.
4. Copy the report worksheets into a new workbook.
5. Convert report formulas to static values.
6. remove external workbook links.
7. apply page/report formatting.
8. create a safe output filename.
9. save the report.
10. repeat for the next entity.
11. log the final result.

The generator also includes a test mode that can limit execution to one client during development.

### `modLogging`

Writes workflow events to:

`tbl_RefreshLog`

The logger captures:

- Timestamp
- Action
- Records
- PASS
- REVIEW
- ERROR
- Unclassified
- Reports Generated
- Duration
- Result
- Details
- User

Logging failures are designed not to stop the primary workflow.

### `modUtilities`

Contains reusable helper procedures for:

- named-range lookup
- named-cell updates
- project-root detection
- folder creation
- filename cleaning
- Excel calculation waiting
- elapsed-time calculations
- formula-to-value conversion
- external-link removal
- report formatting

This avoids duplicating common logic across multiple modules.

## 11. Report Generation Architecture

The report-generation process is intentionally separated from the data-transformation layer.

```text
tbl_ClaimsMaster
       |
       v
Unique Entity List
       |
       v
Set selEntity
       |
       v
Recalculate Reports
       |
       v
Copy Client Summary + Claim Detail
       |
       v
Convert to Static Output
       |
       v
Save Client Workbook
```

Generated files are stored under:

```text
output/
└── client_reports/
    └── YYYY-MM-DD/
```

Each report uses a filename similar to:

```text
Client_Report_<Entity>_YYYY-MM-DD.xlsx
```

The generated client-report directory is ignored by Git by default to prevent repeated production-style outputs from cluttering version control.

One intentionally selected example is stored in:

```text
output/sample-report/
```

for portfolio review.

## 13. Error Handling Strategy

The VBA architecture uses structured error handling around the major workflows.

Errors are captured before cleanup so the original error number and description are preserved.

The report generator also records the stage at which a failure occurred, for example:

```text
Stage: Saving client report
Error 1004: <Excel error description>
```

This makes failures easier to diagnose than a generic macro error.

Application state is restored during error handling, including:

- ScreenUpdating
- EnableEvents
- DisplayAlerts
- StatusBar

Partially generated workbooks are closed where possible to avoid leaving Excel in an inconsistent state.

## 14. Design Decisions

### Excel as the Front End

Excel was intentionally retained because the project represents a realistic reporting environment where business users may already depend on spreadsheet deliverables.

### Power Query for ETL

Transformation logic is kept out of VBA where possible.

Power Query is responsible for data preparation, while VBA handles workflow automation.

This separation improves maintainability.

### One Master Dataset

All reporting is built from `tbl_ClaimsMaster`.

This reduces duplicated logic across dashboards and client outputs.

### Modular VBA

Each module has a focused responsibility.

This makes the automation easier to test, document, and extend.

### Generated Outputs Excluded from Git

Automatically generated client reports are treated as runtime output rather than source code.

This keeps the repository focused on reproducible logic rather than repeated generated files.

## 16. Current Limitations

This project intentionally uses Excel-based architecture for portfolio demonstration.

Potential limitations include:

- source size is constrained by desktop Excel performance
- audit logging is workbook-based rather than database-backed
- report distribution is manual after generation
- source refresh requires desktop Excel
- client permissions are not implemented
- configuration is partly embedded in workbook logic
